# Aniraku v4.2.1 Whole-App Audit

This audit covers the implemented Android routes and supporting services: Home, Catalog, Search, Schedule, Random, Anime Detail, Watch, Library, Profile, Settings, authentication, downloads, synchronization, embedded playback, and release delivery. The user approved every **P0**, **P1**, and **P2** recommendation in this document.

> **Release boundary:** v4.2.1 will improve native behavior and the Android handoff sheet only. The verified main-site Watch player, provider controls, buffering implementation, and playback code are not part of this change set.

## Current Product Strengths

The application already has an unusually complete native anime experience: real AniList discovery and scheduled releases, protected account and library synchronization, anime relationships, 50-item episode pagination, provider selection, direct/proxy/embed source routing, AniSkip, downloads for eligible direct media, and a consistent Nothing OS-oriented visual system. The upcoming work therefore focuses on **truthfulness, recovery, and operational clarity**, rather than redesigning the product or replacing established flows.

## Approved Improvements

| Area | Finding | Approved v4.2.1 improvement | Priority |
|---|---|---|---|
| Embedded providers | The native WebView has a basic popup guard but still permits automatic window initiation and broad non-media navigation. | Strengthen the main-frame navigation allow/deny policy, disable automatic popup windows, retain in-place fullscreen playback, and report a concise recovery state when an unsafe navigation is refused. Apply matching no-redirect behavior to the backend media proxy. | P0 |
| Adaptive native playback | The existing picker handles provider-supplied sources but cannot select actual Media3 tracks from Auto HLS/DASH playback. | Use native `availableVideoTracks` data to expose only supported, actual resolutions; retain Auto by default; preserve selection only for the current episode; no source rebuild or provider refresh. | P0/P1 |
| Reliability testing | Existing tests cover API and native playback logic, but the new remote-release and WebView decision paths have no focused regression coverage. | Add deterministic tests for semantic-version comparison, release metadata parsing, update prompt dismissal, blocked navigation, and quality-track option mapping. | P0 |
| Local diagnostics | Provider failures are hard to distinguish from unavailable tracks or intentionally blocked navigation. | Add bounded, local-only playback diagnostics that redact source URLs and identify only player state, selected quality, buffer state, and navigation decision. | P0/P2 |
| Updates and distribution | The app does not currently detect published direct-distribution updates. | Add a global, optional, cached GitHub release check plus a Settings version row with a manual check action. Present the update sheet only for a real newer published version. | P1 |
| Library and alerts | The Library route correctly shows history, saved titles, and alerts but has no bulk alert action or unread-only filter. | Add **Mark all read** and an **Unread** filter to Alerts. Preserve individual item behavior and guest privacy. | P1 |
| Discovery search | Search has robust rate-limit handling, but fresh searches start empty and have no local continuity. | Persist a small, local-only recent-search list with clear controls; use it only in the blank search state and never send it to the backend. | P1 |
| Download transparency | Eligible direct downloads work, while other source types are correctly excluded; the reason may not always be clear at the action point. | Add a compact “availability reason” line in the Watch download action for embed-only or protected sources, with the existing direct-download behavior untouched. | P1 |
| Watch diagnostics | Playback states are exposed only indirectly through UI behavior and developer logs. | Add a collapsed **Playback status** row in player settings showing provider, delivery type, selected track, and playable buffer when available. It is informational only. | P2 |
| App version clarity | The current app version is not visible in Settings. | Show installed version/build and an update status line in Settings, with an explicit manual refresh action. | P1 |

## Deferred Items

The following improvements were identified but are intentionally **not** included in v4.2.1 because they require broader product, backend, or real-device validation work.

| Deferred area | Why it is deferred |
|---|---|
| Offline downloads for embedded/protected sources | This would misrepresent provider support and risks breaking playback or access constraints. |
| Cross-device personalized recommendations | Requires a new consented recommendation-data design; current discovery is intentionally public AniList data. |
| Push-notification delivery | Requires a production notification service, Android permission flows, and device verification; existing in-app alerts remain intact. |
| Design-system redesign | Current Nothing OS language is coherent; a redesign would be high-risk and unrelated to the reliability update. |
| Device-release verification claims | A real Snapdragon 680 acceptance pass remains separate from source-level tests and cannot be inferred from a build. |

## v4.2.1 Delivery Order

1. Implement isolated native helpers and tests for release checking, semantic versioning, track selection, and navigation blocking.
2. Wire these helpers into the native Watch player, embedded WebView, Settings, Library, Search, and root application shell.
3. Add the backend proxy’s explicit redirect refusal and focused Go tests without modifying website Watch source selection.
4. Bump the application to **4.2.1 / Android versionCode 23**, then validate source, types, native unit tests, and backend tests.
5. Publish the genuine GitHub `v4.2.1` release. Only then update the main-site Android sheet’s visible version label while retaining its `releases/latest` routing.
