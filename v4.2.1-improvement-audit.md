# Aniraku v4.2.1 Improvement Audit

**Scope reviewed:** the current Android v4.2 application, its Expo Video player, native embedded-player WebView, backend media proxy, and the main-site Android handoff sheet. The currently published GitHub release is **v4.2**, with `Aniraku-v4.2.apk`; no v4.2.1 release exists yet. [1]

> **Safety principle:** v4.2.1 should add only isolated, testable improvements. It must not modify the verified browser Watch playback flow, auto-switch providers mid-episode, or claim that a client can remove provider-served advertising from a video stream.

## Requested v4.2.1 Work

| Item | Current state | Proposed v4.2.1 change | Expected user result | Risk control |
|---|---|---|---|---|
| Embed ad / popup / redirect protection | The native WebView already blocks a short list of known advertising-navigation hosts and overrides `window.open`, but it currently enables automatic JavaScript windows and accepts broad navigation. | Tighten the native WebView policy: disable automatic popup creation, retain fullscreen playback, block only main-frame navigations to a curated advertising/tracking list, block unsupported URI schemes, and show an honest recovery state when the provider requires an external navigation. Add equivalent backend redirect refusal for proxied media requests. | Fewer unwanted tabs, redirects, and popups around embedded players. | No source rewriting, no DRM/access-control bypassing, no blanket domain blocking, and no modification to direct/HLS delivery paths that work today. Provider-hosted video ads cannot be reliably removed by the app or backend without changing or breaking the stream. |
| Auto-quality selector | Existing picker can choose provider-supplied resolutions, but an adaptive HLS/DASH source is still displayed as `AUTO` even when Media3 exposes real video tracks. | Add an **Auto / 1080p / 720p / 480p / 360p** selector only when Expo Video reports supported native tracks. It will use the player’s actual track IDs, height, and bitrate; otherwise it keeps the existing provider-resolution picker. | Users can choose an actual available resolution for Kiwi and other adaptive native sources, while Auto remains the default. | Never synthesize resolutions; changing a track does not replace the source, re-fetch the provider, or reset watch position. Track changes are guarded by source identity and actual player capabilities. [2] |
| In-app update prompt | The app has no global release check. The installed application is v4.2 / Android versionCode 22. | On foreground launch, make one short, cached GitHub release request. Compare normalized semantic versions; only show a Nothing OS-style sheet when the published release is newer. It contains **Update now**, **Later**, and release notes. The check fails silently offline or on GitHub errors. | Older users see a clear optional route to the newer direct-distribution APK, without nagging on every screen. | No background polling, no forced update, no account data, and no blocking app startup. Dismissal is persisted per available version. |
| Main-site Android download sheet | The site correctly links to GitHub’s `releases/latest` route, but its visible copy is generic and would be misleading if it claimed v4.2.1 before the release is real. | Once v4.2.1 is published, update visible copy and CTA labels to **V4.2.1**, while retaining the latest-release route. | Android visitors understand which verified build they will download. | This change stays in the Android handoff component only; `Watch.jsx` and its playback code remain untouched. |

## Additional Focused Improvements Worth Including

These are conservative improvements found during the audit. They are independent of visual redesign work and support the requested reliability goal.

| Priority | Improvement | Reason | Inclusion recommendation |
|---|---|---|---|
| P0 | Add test coverage for version comparison, WebView navigation decisions, and native track-choice mapping. | The requested features involve remote data and player state; pure tests prevent accidental regressions. | Include. |
| P0 | Log non-sensitive, local diagnostic reasons when an embed navigation is blocked or a track is unavailable. | Makes provider-specific support failures understandable without exposing URLs or user data. | Include. |
| P1 | Display the installed version and a manual “Check for update” control in Settings. | Gives users a self-service update route without waiting for the optional global prompt. | Include if you approve the update system. |
| P1 | Preserve a manual quality selection for the current episode only, then reset to Auto for a new stream by default. | Prevents an old low-quality preference from unexpectedly restricting a later provider. | Include. |
| P2 | Add an expandable playback diagnostics row showing only player state, selected track, and buffer availability. | Helpful for future field reports, but not required for user-facing playback. | Defer unless you want it. |

## Release and Distribution Sequence

The correct order is to implement and validate the native/backend changes, bump the Android version to **4.2.1 / versionCode 23**, publish the real `v4.2.1` GitHub release, then update the main-site visible label. Until the release exists, the download sheet should continue to identify the actual v4.2 build rather than point users at a non-existent asset.
