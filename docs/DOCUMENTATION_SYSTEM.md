# Documentation System

> **Purpose:** Make every public document feel like part of the Android product: calm, direct, media-led, and useful before it is technical.

## Visual language

| Element | Rule |
| --- | --- |
| Canvas | Near-black `#090909` establishes the branded visual plane in committed SVG headers and dividers. GitHub controls its own page chrome, so repository Markdown remains intentionally clean outside these assets. |
| Type | `#F6F6F2` white is reserved for primary labels in SVG; README copy uses concise display headings, body paragraphs, and compact `code` utility labels. |
| Signal | `#FF4D4D` marks one active action, a thin progress line, or a state cue. It never becomes a decorative flood. |
| Structure | Use image-led hero moments, fine rules, asymmetric screenshot groupings, and space rather than repeated card-like tables. |
| Product proof | Use only the committed real Aniraku screenshots and launcher icon. Do not substitute generated mockups or invented interface claims. |

## Reader flow

| Surface | Reader need | Documentation response |
| --- | --- | --- |
| README hero | What is this and where do I get it? | State the native-product boundary, provide two clear install paths, and foreground the release version. |
| Screenshot spread | Does it feel credible? | Let real Home, Catalog, Watch, and Random captures carry the product story with short captions. |
| Feature beats | What can it do? | Describe discovery, playback, library, and account behavior as four focused product moments. |
| Install and trust | Can I install it safely? | State Android compatibility, direct-install guidance, package migration, integrity, and legal boundaries clearly. |
| Supporting documents | Where do I find a specific policy or process? | Use a consistent compact header, signal line, effective metadata, and a short navigation footer. |

## Editorial rules

Every public page opens with a small `ANIRAKU / ...` utility label, one precise title, and a one-sentence purpose. Legal and security pages remain plain-language and scannable; contribution and architecture pages give actionable steps without turning the document into a wall of setup detail. Screenshots must receive descriptive alt text, and documentation must not claim provider availability, performance, or copyright permissions that the project cannot guarantee.

## Reusable blocks

The README uses the following sequence: branded SVG masthead, launch statement, direct actions, real-screenshot gallery, four product beats, install path, trust/compatibility statement, developer entry point, and a compact document index. Supporting pages reuse the small utility label, title, short purpose statement, a thin visual divider, and a `Back to README` footer.

## Asset QA

Repository SVG text must use broadly available Arial/Helvetica fallbacks rather than platform-specific mono stacks. This keeps the signal labels legible in GitHub, browser previews, and image renderers while preserving their compact, utility-led hierarchy.

## Screenshot QA

The committed `home.jpg` accurately represents the artwork-led Home surface, `catalog.jpg` accurately represents poster-led discovery, `watch.jpg` now accurately represents the native playback and provider-control surface, and `random.jpg` accurately represents the single-title Random surface. Documentation always favors an accurate caption over an attractive but incorrect product claim.
